Assume that you are a senior AI Research Scientist and you need to build an agentic system with following details. Please use best software engineering practices for this. Save the prompt below as it is to keep a track of all points i have told you. Maybe use a markdown to list each one of them.
Master Technical Development Plan and Implementation Prompt
0. Mission
Build an open-source, local-first coding-agent system optimized for a constrained developer workstation and for technically demanding software/research workflows.
The target environment is a Windows workstation with:

* NVIDIA RTX 4060
* 8 GB VRAM
* 16 GB system RAM
* Windows as the primary host environment
* WSL available when a specific repository or toolchain requires Linux, but not the default inference environment
* Git-based software projects
* common development languages including Python, C++, and Rust
* research workloads involving robotics, simulation, reinforcement learning, numerical computation, experiment execution, and analysis.

The target user is not primarily doing CRUD web development. The system must therefore optimize for:

* unfamiliar repository comprehension;
* multi-file implementation;
* research-code modification;
* debugging;
* test/execute/observe/repair loops;
* simulation and experiment execution;
* architecture reasoning;
* numerical/research-code correctness;
* context management;
* efficient local inference;
* safe autonomous execution;
* escalation to a stronger model when necessary.

The goal is not to build another generic chat-with-files application.
The goal is to build a model-agnostic, policy-driven, local-first coding harness capable of making a small local model behave substantially better through orchestration, deterministic tools, verification, context management, and selective escalation.
<assumption>The final repository/package name has not yet been specified. Do not invent a permanent product name during implementation; use a temporary internal package identifier and isolate it so the project can be renamed later without architectural changes.</assumption>

1. Strategic design decision
Do not implement a new coding-agent framework from scratch.
Do not fork OpenCode as the foundation.
Use OpenCode as the user-facing coding-agent substrate and build the differentiated functionality as:
2. OpenCode configuration;
3. OpenCode agents;
4. OpenCode custom tools;
5. OpenCode plugin(s);
6. a model gateway where useful;
7. a replaceable decision/orchestration layer;
8. deterministic research/development tooling;
9. persistent local agent state;
10. evaluation and observability infrastructure.

OpenCode is currently open source under MIT, already includes build/plan agent concepts and subagents, and supports project-level plugins and custom tools.
OpenCode's current custom-tool mechanism allows tools to be added under `.opencode/tools/`, while plugins can extend agents, models, commands, integrations, references, skills, and tools. The current V2 plugin API can also intercept model requests and tool execution.
Therefore the project should treat OpenCode as an upstream runtime dependency and host, rather than as code to be maintained as a fork.
Strategic rule
The project-specific intelligence must live outside the OpenCode core.
Conceptually:

```
OpenCode
    │
    ├── user experience
    ├── sessions
    ├── base agent loop
    ├── standard tools
    ├── permissions
    └── subagent infrastructure
          │
          ▼
   OUR EXTENSION LAYER
          │
          ├── model routing
          ├── micro-decisions
          ├── context control
          ├── verification
          ├── failure classification
          ├── escalation
          ├── research tools
          ├── state
          └── telemetry

```

This gives the project access to OpenCode's continuing upstream development while keeping the project differentiated.
2. Core model stack
The system will use a heterogeneous model hierarchy rather than one universal model.
2.1 Main engineering model: Qwen3.5-9B
Use:

```
Qwen3.5-9B
Q4-class GGUF, preferably Q4_K_M
llama.cpp CUDA
RTX 4060 8 GB

```

Qwen3.5-9B is currently a 9B multimodal model with 262K native context, multi-step prediction training, agentic/tool-use benchmarks, and current support paths for local inference frameworks including llama.cpp-compatible quantizations. Its published results include 65.6 LiveCodeBench v6, 66.1 BFCL-V4, and 18.0 DeepPlanning.
This model is the default engineering model.
It should perform:

* implementation;
* substantial debugging;
* architectural reasoning of moderate complexity;
* test interpretation;
* code review;
* repository modification;
* normal agent tool calling;
* multi-step implementation.

Do not select the 9B model solely because it is the largest model that fits. Select it because its iteration speed and capability are appropriate for the main agent loop.
The main optimization target is:

```
capability × iteration speed × verification

```

rather than raw parameter count.
Required runtime characteristics
The model-serving adapter must expose:

* OpenAI-compatible chat endpoint;
* model identity;
* streaming;
* tool calls/function calling where supported;
* usage metadata if available;
* prompt token counts where available;
* completion token counts where available;
* latency;
* health checks;
* configurable context length;
* configurable generation parameters;
* optional MTP/speculative decoding when the selected runtime/model combination supports it.

MTP must be treated as an optional capability rather than a hard dependency. Detect support during installation/health checks and expose it through configuration.
3. Deep reasoning model: Ternary Bonsai 2 27B
Use:

```
Ternary Bonsai 2 27B
PTQ1_0
PrismML llama.cpp fork
CUDA

```

This is the deep-reasoning / escalation model, not the default model.
The current Bonsai 2 27B distribution provides a 5.95 GB PTQ1_0 representation and a 7.21 GB PQ2_0 representation. Prism specifically documents PTQ1_0 as the better choice when memory is tight and reports that PTQ1_0 is the faster decode packing on Ada-generation cards, which is directly relevant to an RTX 4060. Bonsai also requires the PrismML llama.cpp fork for the custom ternary formats.
Therefore:

```
RTX 4060
    │
    └── Bonsai 27B PTQ1_0

```

must be treated as the initial target configuration.
Do not default to PQ2_0 on an 8 GB card merely because it is faster at prompt processing on some hardware. PTQ1_0 is the selected default because memory is the binding constraint and Ada-class decode characteristics favor it.
Bonsai provides 262K context, vision capability, agentic tool calling and reasoning modes, but the harness should not attempt to exploit the full 262K context by default. Large advertised context is a model capability; it is not an instruction to put huge histories into an 8 GB consumer GPU.
Recommended operating modes:

```
normal deep task:
    16K–24K context

large deep task:
    24K–32K context

very large repository:
    retrieval + summaries
    instead of brute-force 100K+ context

```

These are initial engineering defaults, not immutable claims.
The harness must benchmark them.
Bonsai should be invoked for tasks such as:

* persistent debugging failure;
* difficult architecture reasoning;
* research-methodology decisions;
* difficult algorithmic reasoning;
* cross-module causal analysis;
* high-impact refactoring;
* repeated local-model failure;
* tasks explicitly marked by the user as “deep”;
* situations where the policy engine predicts that the additional reasoning capacity is worth the latency.

It should not automatically replace Qwen for every task.
4. Micro-model: LFM2.5-1.2B-Thinking
Add:

```
LFM2.5-1.2B-Thinking
CPU-resident
GGUF / llama.cpp

```

LFM2.5-1.2B-Thinking is a 1.17B-parameter model with 32,768-token context; Liquid provides a GGUF specifically optimized for llama.cpp and local/CPU deployment. Liquid explicitly recommends it for agentic tasks, data extraction, and RAG, while explicitly saying it is not recommended for knowledge-intensive tasks and programming. That makes it a poor main coder but a potentially excellent micro-controller/subagent.
This distinction is critical.
LFM must not be assigned primary implementation responsibility.
Use it for bounded, operational tasks:

```
repo exploration
file triage
failure classification
context relevance decisions
tool routing
subagent routing
escalation decisions
loop detection
completion classification
log summarization
experiment artifact classification
cheap structured decisions

```

Liquid also documents native function calling for LFM2.5 and provides a llama.cpp deployment path, making it appropriate for lightweight local tool-oriented work.
The official model card also reports BFCLv3 56.97 for LFM2.5-1.2B-Thinking, confirming that tool-use capability is a meaningful part of its intended profile, while the same card's programming caveat should be respected.
Initial LFM generation defaults
Use the model's documented low-temperature reasoning settings as the baseline:

```
temperature = 0.05
top_k = 50
repetition_penalty = 1.05

```

Then benchmark before changing them.

8. Do not make LiteLLM mandatory for MVP
LiteLLM is useful, but it should be treated as an optional infrastructure component rather than embedded into the fundamental agent loop.
LiteLLM currently supports OpenCode as a harness and can expose model groups through a gateway. It also has current first-class TypeSafe/Jev support, including `/v1/decisions`, `/systemone`, model routing and Jev-based context-compaction behavior.
Therefore the architecture should support:


```
OpenCode
    ↓
direct local model endpoints

```

as the minimal mode.
And optionally:

```
OpenCode
    ↓
LiteLLM
    ↓
local/cloud/decision providers

```

as the advanced mode.
This avoids adding a network/gateway dependency to every local install.
9. Jev integration
Jev must be implemented as an optional DecisionEngine backend.
TypeSafe currently positions Jev as a structured decision model: software submits state and typed questions and receives structured probabilistic decisions rather than free-form text. It is intended for classification, routing, scoring, verification, branching and workflow control.
Current LiteLLM versions support TypeSafe Jev directly, including a TypeSafe pass-through, a decision API, Jev-based routing, and an optional tool-result compaction guardrail.
Implement:

```
DecisionEngine
    ├── RulesDecisionEngine
    ├── LFMDecisionEngine
    ├── JevDecisionEngine
    └── FutureLearnedDecisionEngine

```

The rest of the system must not know which backend is active.
Example decision contract

```
interface DecisionEngine {
    decide<T extends DecisionSchema>(
        state: DecisionState,
        schema: T
    ): Promise<DecisionResult<T>>;
}

```

A decision result should include:

```
{
  "decision": "ESCALATE",
  "confidence": 0.86,
  "reason_code": "REPEATED_TEST_FAILURE",
  "provider": "lfm",
  "latency_ms": 112
}

```

For Jev, preserve its probabilistic output.
For LFM, generate a strict structured response and validate it.
For rules, compute deterministic confidence or mark confidence as `null`.
The host software—not the model—must remain the authority.

12. Do not build a multi-agent swarm
The design must explicitly reject the following:

```
architect
researcher
coder
tester
debugger
security agent
documentation agent
benchmark agent
manager agent

```

all running freely and recursively.
This introduces:

* context explosion;
* duplicated reasoning;
* high latency;
* increased memory consumption;
* inconsistent conclusions;
* difficult debugging;
* difficult evaluation.

Instead, create a hierarchical agent:

```
MAIN QWEN
    │
    ├── ask LFM for cheap evidence
    │
    ├── invoke deterministic tools
    │
    ├── invoke review subagent when useful
    │
    └── escalate to Bonsai only when justified

```

Subagents should return evidence or bounded analysis, not arbitrary full autonomous branches.
13. Subagent output policy


18. Escalation policy
Default:

```
Qwen → Qwen → Qwen

```

If progress stalls:

```
LFM:
    classify state

```

If the result indicates persistent or high-complexity failure:

```
Bonsai

```

Example escalation triggers:

```
same normalized failure >= 2
different patches produce same failure
architecture uncertainty is high
cross-module behavior is involved
research methodology question
user explicitly requests deep reasoning
high-impact change

```

After Bonsai returns:

```
Bonsai:
    analyze / propose

Qwen:
    implement / test

```

Do not allow Bonsai to automatically mutate code during the first implementation stage.
This separates:

```
deep reasoning

```

from:

```
high-frequency engineering iteration

```

which is the intended value of the heterogeneous model architecture.
19. Failure normalization
The system must recognize that these are semantically similar:

```
AssertionError:
expected 0.5
got 0.7

```

and:

```
assertion failed: torque norm outside limit

```

Do not use exact-string repetition detection only.
Normalize failures by:

* exception type;
* command;
* test identifier;
* source location;
* key message tokens;
* stack trace signature;
* exit code.

Generate:

```
FailureFingerprint

```

with stable hashing.
This enables robust loop detection.
20. Loop detection
The system must detect:

```
same command repeated
same patch repeated
same failure repeated
same file repeatedly rewritten
no metric progress
same test failing across attempts

```

When a loop is detected, the system should stop blindly continuing and invoke the decision engine.
Example:

```
3 iterations
2 identical failure fingerprints
0 improvement

```

→ classify as `STALLED`.
Then:

```
STALLED
    ↓
LFM/Jev decision
    ↓
ESCALATE / REPLAN / ASK_USER

```

24. Optional Jev context compaction
Jev can later be used to decide whether an old tool result is still relevant.
This is directly aligned with the current LiteLLM/TypeSafe pattern, where Jev can judge whether historical tool output is still required and replace irrelevant results with a compact marker.
Design:

```
Tool result
    ↓
ContextManager
    ↓
DecisionEngine
    ↓
KEEP / COMPACT / DROP

```

Do not make this mandatory for MVP.
First implement deterministic age/type rules:

```
keep current test
keep current diff
keep current error
drop stale directory listing

```

Then add LFM or Jev for ambiguous cases.

32. Use stable OpenCode APIs where possible
Current OpenCode V2 plugin hooks expose powerful request/tool interception, but the V2 plugin API is explicitly marked beta and may change.

4. implement graceful degradation;
5. document the supported OpenCode version range;

65. Final engineering philosophy
The project should follow five principles.
66. Models are replaceable.
Do not architect around Qwen, Bonsai, LFM, or Jev-specific assumptions.
67. The harness owns state.
Do not make the model responsible for remembering the workflow.
68. Deterministic systems own truth.
Tests, compilers, Git, parsers, simulators and metric calculators provide evidence.
69. Cheap intelligence handles cheap decisions.
Use rules/LFM/Jev for routing, classification and operational decisions.
70. Expensive intelligence is reserved for high-value reasoning.
Use Qwen for normal engineering and Bonsai for genuinely difficult reasoning.
The final system should therefore behave less like:


```
"One giant model with a huge prompt"

```

and more like:

```
"An intelligent software control system
that allocates reasoning where it is valuable."

```

That is the central architectural thesis of this project.
